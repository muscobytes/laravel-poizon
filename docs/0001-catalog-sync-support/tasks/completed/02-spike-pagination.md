## Зависимости

Нет. Может исследоваться независимо от остальных спайков.

## Цель

Определить поддерживаемые размеры страниц, курсор продолжения и проверяемое условие завершения обхода нового API.

## Методика и контрольные примеры

1. Для SPU проверить `pageSize` 1, 199, 200, 201, 500, 2000; для SKU — 1, 1999, 2000, 2001. Проверить запрос без параметра. Для исследования отклоняемого SDK значения использовать изолированный экспериментальный адаптер по спецификации, не менять стабильную валидацию.
2. Выбрать ограниченный исторический набор с достаточным числом записей, чтобы отличить принятие размера от молчаливого серверного ограничения. Сохранить запрошенное и фактическое количество, ошибки, `lastId`, `hasMore`, `total` и их типы/присутствие.
3. Установить источник следующего `startId`: поле ответа либо подтверждённый ID записи. Не подменять его автоматически `dwSpuId`/`dwSkuId`.
4. Воспроизвести последнюю полную страницу, последнюю неполную страницу и пустой ответ; установить критерий конца, включая поведение при отсутствии метаданных. Короткая страница сама по себе не доказывает конец.
5. Полностью обойти один контрольный набор с разными размерами страниц. Сравнить множества ID, проверить продвижение курсора, повторы и отсутствие потерь. Зависание или противоречие метаданных — блокер, а не повод пропустить страницу.
6. Отдельно сопоставить PDF (SPU до 200), текущий валидатор (до 2000) и фактическое поведение сервера. Зафиксировать безопасный размер для примеров и совместимый способ документирования ограничения.

## Ожидаемые артефакты

- Отчёт `reports/02-pagination.md` с матрицей размеров, трассой курсоров и сравнением множеств ID.
- Правила размеров, пагинации и завершения в спецификации и документации пакета; ссылка на отчёт в README проекта.

## Проверка

Успешный HTTP-ответ не доказывает применение `pageSize`. Серверное ограничение отличено от малого контрольного набора. Нельзя объявлять полный обход успешным при неразрешённых пропусках или неизвестном критерии конца.

## Вне объёма

Автопагинация SDK, обход всего production-каталога, изменение прежнего валидатора и реализация очередей. Несовместимые исправления оформляются отдельно.

## Готово, когда

- Для SPU и SKU определены подтверждённый размер страницы, источник курсора и критерий конца.
- Сравнение обходов доказывает полноту контрольного набора; блокирующие противоречия разрешены.
- Отчёт существует, доступен из README, выводы внесены в спецификацию и документацию пакета, расхождение PDF/SDK явно описано.

## Результаты выполнения

28.11.2026 выполнены 36 ограниченных живых чтений и 34 offline-проверки. [Отчёт](../../reports/02-pagination.md) и [очищенные наблюдения](../../reports/evidence/02-pagination.jsonl) фиксируют серверные пределы SPU 200 / SKU 2000, default 100 / 500, отсутствие `lastId`/`hasMore`, исключительную границу `startId` по полю `id`, полноту двух контрольных наборов при разных размерах и завершение пустой страницей. Текущая проверка SDK для SPU допускает значения, отклоняемые upstream; это расхождение задокументировано, продуктовый код не изменён. Выводы включены в общие документы, исследование принято 28.11.2026.

## Решения реализации

Приняты серверные пределы SPU 200 / SKU 2000 и defaults 100 / 500. Пример: SPU pageSize201 получает HTTP200/code10002001; это ошибка, не пустой каталог. Следующий startId берётся из max(id), конец — успешная пустая страница. Валидация SDK не менялась; её расхождение описано в документации. Продуктовые классы SDK не изменялись. Исследовательские сценарии и очищенные наблюдения хранятся в reports/ проекта; они запускаются вручную, не создают кэш или credentials и не подключаются к CI. Результаты отражены в [документации пакета](../../../catalog-sync.md) и [спецификации](../../spec.md).
