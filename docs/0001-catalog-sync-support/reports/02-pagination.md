Результат: обязательные проверки пагинации выполнены на ограниченных наборах; выводы включены в [документацию пакета](../../catalog-sync.md). Обход всего каталога не выполнялся.

## Окружение и методика

- Исследуемая ревизия SDK: `1898169f1fd0e94e909f4ab8950481da6fde0173` с текущими незакоммиченными проектными документами. Продуктовый код SDK не изменён.
- Offline-проверка: Docker-образ `poizon-package-test:8.2`, PHP 8.2, пакет смонтирован только для чтения, сеть отключена.
- Живые чтения: существующий production PHP-контейнер приложения, ревизия `53e06e155098dc69b26e25c09c398e779d4fd8d4`, подключение `global` (псевдоним направления, без ID авторизации). Использован [общий read-only bootstrap](./scripts/01-live-bootstrap.php).
- Bootstrap выбирает действующий access token в read-only транзакции с rollback и расшифровывает только в памяти. `resolve`, refresh, покупки, записи credentials и файлов на сервере не выполнялись. HTTP Factory изолирован от listeners; каждый запрос имел ровно одну отправку, retry отключён.
- В production использовались `App\Services\PoizonOpenPlatformSigner` и `PoizonJsonTransport` — предшественники классов самостоятельного SDK. Это исследование upstream-протокола, а не end-to-end проверка установленного нового пакета.
- Выполнено **36** бизнес-чтений Poizon: 12 в матрице параметров, 20 в четырёх ограниченных обходах и 4 для проверки default на достаточных наборах. Пауза между чтениями — 300 мс. Все HTTP-ответы — 200; бизнес-отказы сохранены отдельно от успешных пустых ответов.

Сохранены [36 очищенных наблюдений JSONL](./evidence/02-pagination.jsonl): только название эксперимента/метода, бизнес-параметры, HTTP/upstream-коды, число отправок, количество записей, метаданные и разрешённые товарные ID/временные метки. OAuth envelope, подписи, credentials и полные ответы не сохранялись.

Дополнительно официальный публичный клиент документации исследован в одноразовом Docker-контейнере. Два анонимных metadata GET для SPU/SKU вернули HTTP 401 / code 401; содержимое metadata не использовано как подтверждение контракта. Эти два запроса не входят в 36 бизнес-чтений.

## Размеры страниц: локальная и серверная проверки

[Мануал](../sources/poizon-open-api-integration-guide-1029.pdf), стр. 13 и 17: SPU — 1–200, default 100; SKU — 1–2000, default 500.

Матрица живых запросов использовала `dwSpuId=[10903]`, `startId=0`, направление `global`:

| Метод | `pageSize` | HTTP / code | Количество | Вывод |
| --- | --- | --- | --- | --- |
| SPU | 1, 199, 200 | 200 / 200 | 1 в каждом ответе | Параметры приняты; небольшой набор не доказывает фактическую вместимость страницы |
| SPU | 201, 500, 2000 | 200 / 10002001 | Данных нет | Сервер явно отклоняет значения выше 200, а не молча ограничивает страницу |
| SPU | отсутствует | 200 / 200 | 1 | Запрос без параметра допустим; default отдельно проверен на большем наборе |
| SKU | 1 | 200 / 200 | 1 | Сервер применяет ограничение размера |
| SKU | 1999, 2000 | 200 / 200 | 25 в каждом ответе | Допустимые значения, но на этом наборе максимум вместимости не измеряется |
| SKU | 2001 | 200 / 10002001 | Данных нет | Сервер явно отклоняет значение выше 2000 |
| SKU | отсутствует | 200 / 200 | 25 | Запрос без параметра допустим; default отдельно проверен на большем наборе |

У отклонённых запросов отсутствие данных не является успешным пустым каталогом: `code != 200` обязателен к обработке как ошибка.

Для проверки default и исключения вывода по слишком маленькому ответу выполнены ещё четыре чтения:

| Метод и ограниченный фильтр | Явный размер / получено | Размер отсутствует / получено | Сравнение |
| --- | --- | --- | --- |
| SPU, `dwSpuId=10903..11102` (200 запрошенных ID) | 200 / 164 | отсутствует / 100 | Те же первые 100 ID; `total=164` |
| SKU, `dwSpuId=10903..11002` (100 запрошенных ID) | 2000 / 1443 | отсутствует / 500 | Те же первые 500 ID; `total=1443` |

Таким образом, наблюдались default **100 SPU** и **500 SKU**. Нет признаков молчаливого ограничения SPU до 100 или SKU до 500 при явном большем размере: сервер вернул соответственно 164 и 1443 записи. Ровно 200/2000 записей на странице не требовалось для определения отказа выше документированного максимума; фактические страницы из 200/2000 элементов этим экспериментом не наблюдались.

[Offline-сценарий](./scripts/02-local-pagination.php) подтвердил текущую реализацию: и конструктор, и `fromArray()` обоих Query принимают 1, 199, 200, 201, 500, 1999, 2000 и отклоняют 2001. Итого 32 проверки путей создания плюс 2 проверки DTO. Это **расхождение SDK с сервером для SPU 201–2000**, а не поддержка таких размеров Poizon. Скрыто ужесточать прежнюю проверку в совместимом выпуске не следует; в примерах использовать SPU ≤ 200 и SKU ≤ 2000.

## Метаданные и источник курсора

Во всех успешных бизнес-ответах этого исследования:

- `data.lastId` отсутствует, `data.hasMore` отсутствует. Это отсутствие полей, а не явный `null` и не `hasMore=false`.
- `data.total` присутствует как JSON integer. На непустых страницах он равен общему размеру отфильтрованного набора, а не числу оставшихся записей: 8 для SPU и 25 для SKU. На завершающем пустом ответе наблюдался `total=0`.
- Каждая запись содержит отдельное поле `id`. Курсор продолжения — максимальный `id` предыдущей страницы; **не** `dwSpuId` и **не** `dwSkuId`.
- `startId` действует исключительно: все записи следующей страницы имеют `id > startId`. Повторной выдачи граничной записи и дубликатов в контрольных обходах не было.

Пример SPU: товар `dwSpuId=10903` имеет `id=311943`. Пример SKU: `dwSkuId=65412561` имеет `id=4522053`. Эти идентификаторы обозначают разные сущности и не взаимозаменяемы.

Поле `id` не типизировано отдельным свойством `Spu`/`Sku`, но уже доступно через `extraFields['id']`. Сохранять точное значение без float. Существующие nullable `lastId`/`hasMore` в DTO не означают, что upstream обязан их вернуть. Offline-проверка также подтвердила различение отсутствия/null и сохранение строкового курсора `9007199254740993` без потери точности.

## Полнота и завершение обхода

Все бизнес-параметры каждого запроса сохранены в JSONL. Между страницами менялся только `startId`.

| Контрольный набор | Размер | Количество по страницам, включая пустую | Уникальных `id` | Последний курсор |
| --- | --- | --- | --- | --- |
| SPU `dwSpuId=10903..10910` | 2 | 2, 2, 2, 2, 0 | 8 | 512220 |
| Тот же SPU-набор | 3 | 3, 3, 2, 0 | 8 | 512220 |
| SKU `dwSpuId=[10903]` | 5 | 5, 5, 5, 5, 5, 0 | 25 | 1363955921 |
| Тот же SKU-набор | 7 | 7, 7, 7, 4, 0 | 25 | 1363955921 |

Множества `id` при двух размерах для каждого метода полностью совпали; число уникальных записей совпало с `total` непустых страниц. Проверены последняя полная страница, последняя неполная и следующий пустой ответ. Курсор на каждом шаге продвигался, повторов не было.

Подтверждённая процедура приложения для такой выдачи:

1. Зафиксировать фильтры (в том числе окно времени, если применяется) и допустимый размер страницы; начать с `startId=0` либо сохранённого точного курсора.
2. На HTTP/business-ошибке не завершать обход как успешный и не передвигать прогресс.
3. На успешной непустой странице обработать записи, проверить продвижение `id` и продолжить с максимальным `id`. Не заменять его товарным ID.
4. Для однозначного завершения читать до успешной пустой страницы. Не полагаться на отсутствующие `lastId`/`hasMore`, короткую страницу или `total` как число оставшихся записей.
5. Watermark и подтверждение записи страницы остаются обязанностью приложения. SDK не выполняет автопагинацию.

Это доказательство полноты **контрольных отфильтрованных наборов**, а не гарантия консистентного снимка всего изменяемого каталога. Поведение при одновременном изменении записей и семантика временного фильтра относятся к отдельному спайку 01.

## Воспроизведение и итог

- [Матрица параметров](./scripts/02-live-pagination.php): после bootstrap направить тело без второго `<?php` в stdin PHP существующего контейнера; 12 чтений по одному SPU.
- [Ограниченные обходы](./scripts/02-live-walk.php): аналогичный запуск; максимум 8 страниц на каждый из четырёх обходов, фактически 20 чтений.
- [Default на достаточных наборах](./scripts/02-live-defaults.php): 4 чтения, фильтры и параметры зафиксированы в сценарии.
- Offline: запустить `02-local-pagination.php` в Docker из корня SDK с доступным `vendor/autoload.php`, сетью `none` и read-only mount. Проверка выполнена успешно; Pint `--test` для offline-сценария прошёл.

Новых blocking-неизвестных по критериям задачи 02 не осталось: пределы и default согласуются с PDF, источник курсора и завершение подтверждены живым обходом, контрольные множества совпали. Документация должна явно отражать отсутствие `lastId`/`hasMore` и расхождение локального SPU-валидатора. Реализация SDK и выпуск этим спайком не выполнялись.
