## Окружение и воспроизведение офлайн-части

Сценарий запущен в одноразовых Docker-контейнерах без сети (`--network none`) и с read-only файловой системой. Репозиторий подключён только для чтения в `/package`; используется его Composer autoload. Сценарий не читает credentials, не запускает приложение и не обращается к OAuth/Poizon.

Исторический сценарий ниже воспроизводится на baseline `1898169f1fd0e94e909f4ab8950481da6fde0173` с установленными зависимостями. После задачи 05 числовой `Spu.distSpuId` принимается; проверка его прежнего отказа намеренно больше не проходит на новом коде. Актуальные регрессии находятся в `tests/CatalogSyncTest.php`. Первичные JSONL и результаты спайка не изменены.

Из корня baseline-репозитория:

```sh
docker run --rm --network none --read-only \
  --mount "type=bind,source=$PWD,target=/package,readonly" \
  poizon-package-test:8.2 \
  php /package/docs/0001-catalog-sync-support/reports/scripts/04-response-contract.php

docker run --rm --network none --read-only \
  --mount "type=bind,source=$PWD,target=/package,readonly" \
  php:8.4-fpm-alpine \
  php /package/docs/0001-catalog-sync-support/reports/scripts/04-response-contract.php
```

Нужны уже установленные dev-зависимости репозитория и соответствующие локальные Docker-образы. Фактические версии: PHP 8.2.36 и 8.4.28, 64-bit. Результат на каждой версии — `count=15`, все проверки `true`. Это наблюдение текущего поведения SDK, а не тест будущего исправления.

## Доказано синтетическими проверками

| Вход / проверка | Наблюдаемый результат |
| --- | --- |
| JSON-число `dwSkuId: 9007199254740993` через настоящий `ResponseDecoder` и `Sku::fromArray()` | Строка `"9007199254740993"` без округления |
| JSON-число `dwSkuId: 9223372036854775808` через тот же путь | Строка `"9223372036854775808"`; `JSON_BIGINT_AS_STRING` сохраняет значение за пределом signed 64-bit |
| `distSkuId` со строковыми значениями тех же больших ID | Строки сохранены |
| `Spu.distSpuId: 12345` (целое число) | `ProtocolException`, поле `distSpuId` |
| `Spu.distSpuId: "12345"` | Строка принята |
| `Spu.distSpuId: "opaque-dist-id"` | Строка принята без ограничения одними цифрами |
| `dwSkuId` типа float | `ProtocolException` |
| `productDesc: "<p>synthetic description</p>"` | Доступно в `extraFields['productDesc']`; `has('productDesc')` — true; поле присутствует в `fields()` |
| `modifyTime: 1795800000000` | Целое значение сохранено в `extraFields` |
| Дополнительное вложенное поле `{'nullable': null, 'enabled': false}` | Структура, `null` и `false` сохранены |
| `image: null` и отсутствующий `dwSpuTitle` | В обоих свойствах null; `has('image')` — true, `has('dwSpuTitle')` — false |
| Вложенный SKU с неизвестным `barcode` | Доступен через `spu->skuList[0]->extraFields['barcode']` |
| Неизвестный `fulfillmentMode: "FUTURE_MODE"` | Значение сохранено строкой без бизнес-интерпретации |
| `AuthorizationReference::forConnection('catalog-fast')` | Ссылка хранит выбранное имя подключения; соответствие имени реальному каналу этим не доказывается |

Потери точности в текущем декодере не обнаружено. Проблема числового SPU `distSpuId` — несовместимость типа ответа с текущей схемой DTO: значение отклоняется, а не округляется.

Проверка описаний доказывает сохранение дополнительного строкового поля SDK. Наличие реального `productDesc`, его наполненность, формат HTML и допустимость отображения HTML в приложении этим не доказаны.

## Каналы: документировано и наблюдалось ранее

Мануал описывает `fulfillmentMode` как способ исполнения; его известные значения — `NORMAL`, `DIRECT_SEND`, `DEPOSIT`. Это не описание фильтра Fast/Global.

Исторический протокол от 18.11.2026 сообщает:

| Метод | Fast | Global | Условия прежней проверки |
| --- | --- | --- | --- |
| `querySpuList` | HTTP 200 / code 200 | HTTP 200 / code 200 | Точные товарные фильтры, разные авторизации, без `distPlatform` |
| `querySkuList` | HTTP 200 / code 200 | HTTP 200 / code 200 | Один dw SKU, разные dist ID |
| `querySkuDetail` | HTTP 200 / code 200 | HTTP 200 / code 200 | Скалярный dw SPU и массив dw SKU |
| `querySkuBidPrice` | HTTP 200 / code 200 | HTTP 200 / code 200 | Массив `dwSkuIds`, `hasPrice=true` |

Для контрольного SKU `65412613` прежняя проверка вернула Fast `36600`/`DEPOSIT`, Global `36400`/`NORMAL`; для `65412626` — `39700`/`DEPOSIT` в обоих направлениях. Поэтому правило «DEPOSIT означает Fast» противоречит уже имеющимся наблюдениям. Это исторические цены, не актуальная котировка.

## Текущая живая проверка

28.11.2026, 01:09:56–01:10:03 +03:00, выполнены восемь чтений из действующего production app. Число отправок — 8, по одной на запрос; все HTTP 200 / upstream `code=200`. Развёрнутая ревизия приложения по данным окружения — `53e06e155098dc69b26e25c09c398e779d4fd8d4`.

Использован [общий read-only bootstrap](./scripts/01-live-bootstrap.php) и [сценарий матрицы](./scripts/04-live-matrix.php), переданные в PHP через stdin без создания файлов в приложении. Bootstrap читает связь подключения с авторизацией в SQL-транзакции READ ONLY с rollback, расшифровывает access token только в памяти и не вызывает `resolve`, refresh или сохранение credentials. Применены существующие production signer/transport `App\Services\PoizonOpenPlatformSigner` и `App\Services\PoizonJsonTransport` — предшественники выделенного SDK; живой вызов именно нового `PoizonClient` этим не доказан. Для эксперимента выбран отдельный HTTP factory без слушателей, повторы выключены. Ошибки выводились бы только именем класса.

[Очищенные текущие наблюдения JSONL](./04-live-observations.jsonl) содержат явный allowlist товарных данных, бизнес-параметры, типы и имена полей; OAuth envelope и credentials в файл не выводились. Псевдоним `channel-A` соответствует Fast, `channel-B` — Global.

| Метод / бизнес-параметры | Fast (`channel-A`) | Global (`channel-B`) |
| --- | --- | --- |
| `querySpuList`: `dwSpuId=[10903]`, `pageSize=1`, `querySku=true` | 1 SPU, 25 вложенных SKU | 1 SPU, 25 вложенных SKU |
| `querySkuList`: `dwSkuId=[65412613]`, `pageSize=1` | 1 SKU | 1 SKU |
| `querySkuDetail`: `dwSpuId=10903`, `dwSkuId=[65412613]` | 1 SKU, есть `spuBasicAttr` | 1 SKU, есть `spuBasicAttr` |
| `querySkuBidPrice`: `dwSkuIds=[65412613,65412626]`, `hasPrice=true` | 2 элемента | 2 элемента |

`distPlatform` и предполагаемые параметры выбора канала не передавались. Для проверенных чтений выбора действующей авторизации достаточно. Проверка относится к этим двум подключениям и контрольным ID, не ко всем возможным конфигурациям аккаунтов.

### Наблюдаемые типы и данные

- В обоих SPU `dwSpuId` — int `10903`; `distSpuId` — UUID-строка. У Fast и Global dist ID различаются. Числовой SPU `distSpuId` в живых ответах **не наблюдался**; его приём остаётся совместимым расширением по PDF и синтетической регрессии.
- Для SKU `65412613` `dwSpuId`, `dwSkuId` и `modifyTime` — int, `distSpuId` и `distSkuId` — UUID-строки. Список и карточка одного подключения согласованы по ID; между подключениями dw ID совпадают, dist ID различаются.
- Fast `modifyTime` SKU — `1795788167000`, Global — `1795790677000`. SPU Fast — `1787181336000`, Global — `1787786149000`. Это снимки, не доказательство реакции `modifyTime` на смену цены.
- Реальный `productDesc` присутствует как непустая китайская строка в обоих SPU. Очищенное начало описания сохранено в JSONL (не более 300 символов). Также присутствуют дополнительные `baseImage`, `material`, `sizeChart`, `season`, `style`, `authPrice` и категории. Типизированного `productDesc` для доступа через `extraFields` не требуется.
- У SKU есть `saleAttr` (2 элемента) и `sizeInfos` (6 элементов). Наблюдаемые имена атрибутов: `cnValue`, `cnName`, `level`, `enName`, `enValue`; размер: `sizeKey`, `sizeValue`. В карточке дополнительно есть `spuBasicAttr`; в списке его нет.
- Вложенный в SPU SKU содержит `dwSkuId`, UUID `distSkuId`, `saleAttr`, `sizeInfos`, `modifyTime`, `barcode` и `fulfillmentMode`; родительские dw/dist SPU ID в этом вложенном объекте отсутствуют. SDK не должен требовать их присутствия или автоматически синтезировать их.
- В ценовых ответах `dwSkuId` и `minBidPrice` — int; также присутствуют `supplementPrice`, `deliveryTime`, `fulfillmentModeDesc`. В этих элементах нет `distSkuId`: опциональное свойство DTO должно оставаться отсутствующим/null, без подстановки из каталога.
- SKU `65412613`: Fast `36900` / `DEPOSIT`, Global `36700` / `NORMAL`. SKU `65412626`: Fast `39700` / `DEPOSIT`, Global `39400` / `DIRECT_SEND`. Это значения на момент эксперимента, а не текущие обещанные цены и не доказательство единиц валюты само по себе.

Синтетическая проверка использует настоящий декодер SDK и DTO, а живая матрица показывает формы реального протокола. Полное воспроизведение всех необрезанных текущих ответов через `PoizonClient` не выполнялось: сохранена безопасная проекция и имена остальных полей. Эта граница проверки должна сохраняться в документации; полноценные HTTP-фикстуры и регрессии относятся к задаче 05.

Публичные страницы методов 200002, 200003, 200004 и 200021 повторно запрошены web-инструментом: содержимое недоступно этим инструментом. Такая ошибка не подтверждает ни изменение контракта, ни отключение метода API.

## Минимальные выводы для реализации и оставшиеся условия

1. Сохранить выбор подключения через `AuthorizationReference`; не встраивать в SDK сопоставление имён с Fast/Global. Текущая живая матрица подтверждает достаточность выбора авторизации для проверенных методов и подключений.
2. Не вводить предположительный enum `distPlatform` или интерпретацию `fulfillmentMode` как канала.
3. В задаче 05 дополнительно принять неотрицательное целое SPU `distSpuId` и вернуть строкой, сохранив существующие opaque-строки. Числовой вариант описан в PDF и воспроизведён синтетически как текущий отказ; в текущих живых ответах не наблюдался.
4. Сохранить `JSON_BIGINT_AS_STRING`, отказ от float для ID, `extraFields` и присутствие полей. Для описаний, `modifyTime` и дополнительных вложенных полей новый типизированный API по офлайн-проверке не требуется.
5. Оба подключения проверены по одинаковым dw ID; реальные описания и формы ID зафиксированы. Блокирующих вопросов в области задачи 04 не осталось. Выводы включены в спецификацию и публичную документацию; правила окон, полноты обхода и снятия SKU относятся к другим спайкам и не доказываются этим результатом.
