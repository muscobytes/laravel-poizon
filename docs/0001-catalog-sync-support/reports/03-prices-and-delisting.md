## Окружение и методика

Ревизия SDK: `1898169f1fd0e94e909f4ab8950481da6fde0173`. Для живых чтений использован существующий production Docker-контейнер приложения с образом SHA `53e06e155098dc69b26e25c09c398e779d4fd8d4`. В нём установлены предшественники SDK — `App\Services\PoizonOpenPlatformSigner` и `PoizonJsonTransport`. Их переиспользовали без дублирования подписи. Это наблюдение протокола через существующий runtime, а не сквозной тест нового `PoizonClient`.

Bootstrap читает active credentials внутри PostgreSQL READ ONLY transaction с rollback, расшифровывает только access token в памяти процесса и проверяет срок действия. OAuth resolve/refresh, запись credentials, покупки и изменения каталога не выполнялись. Используется отдельный HTTP Factory без приложения-логирования тела, retry выключен, одна отправка на запрос, пауза 500 мс между запросами.

Псевдонимы: `channel-A` — Fast, `channel-B` — Global. Контроль: SPU `10903`, SKU `65412613`, `65412626`, `65412648`. Запросы двух подключений выполнялись последовательно, поэтому их цены не являются атомарным снимком.

Для каждого подключения выполнено семь запросов: список трёх SKU; SPU с вложенными SKU; цены без `hasPrice`, с `false` и `true`; списки с deprecated `distStatus=PRODUCT_ON` и `PRODUCT_OFF`. Ещё два запроса Global проверили размеры массива цен 200 и 201. Четыре повторных чтения SKU и цены завершили минутное сравнение снимков. Основная матрица и повторные снимки: 20 HTTP-отправок, все HTTP 200; 19 с `code=200`, один с `code=500080002` для массива 201 ID. Затем выполнены два точных уточнения `supplementPrice` и два ограниченных поиска OFF-записей без товарного фильтра. Всего 24 исследовательских запроса: 23 с зафиксированным HTTP 200 (22 `code=200`, один `code=500080002`), один завершился `JsonException` при разборе ответа; его HTTP/upstream-коды не сохранены. Повторов не выполняли. Подтверждённых 429/OAuth-отказов не наблюдалось; неизвестный ответ ошибочного запроса не классифицировался как успешный или пустой.

Сохранялась только явная проекция: время, псевдоним, бизнес-параметры, HTTP/code/attempts, имена полей, товарные ID, статус, цена, `modifyTime`, `fulfillmentMode` и типы значений. Credentials, подписи, OAuth envelope, исходные ответы целиком и сообщения исключений не сохранялись.

## Наблюдалось: списки и ценовой метод

В обоих подключениях `querySkuList` вернул все три SKU. Во всех этих записях и соответствующих вложенных SKU `querySpuList(querySku=true)` **поле `minBidPrice` отсутствовало**. Это отсутствие поля, не `null` и не цена 0. Наблюдение относится к проверенным ответам, а не утверждает, что API никогда не отдаёт цену в списках.

| Метод цен для трёх контрольных ID | Fast | Global |
| --- | --- | --- |
| Без `hasPrice` | 3 элемента: два с ценой, `65412648` с `dwSkuId` и `supplementPrice`, без `minBidPrice`/`fulfillmentMode` | Аналогично |
| `hasPrice=false` | Только `65412648`, без поля цены | Аналогично |
| `hasPrice=true` | Только `65412613` и `65412626`, оба с ценой | Аналогично |

Наблюдаемые цены `minBidPrice`:

| SKU | Fast | Global |
| --- | --- | --- |
| `65412613` | `36900`, `DEPOSIT` | `36700`, `NORMAL` |
| `65412626` | `39700`, `DEPOSIT` | `39400`, `DIRECT_SEND` |
| `65412648` | Нет основного `minBidPrice` в проверенном ответе | Нет основного `minBidPrice` в проверенном ответе |

Это исторические котировки на момент эксперимента, не актуальная рекомендация цены. Все наблюдаемые цены — JSON Integer; ноль и явный `null` на этих SKU не встретились. Поле `currency` в ценовых элементах отсутствовало. В двух дополнительных чтениях без `hasPrice` у всех трёх контролей в обоих подключениях `supplementPrice=[]`. У SKU `65412648` полный набор имён полей — `supplementPrice`, `dwSkuId`; это не буквально элемент с единственным полем ID. Пустой supplementary-массив и отсутствие основного `minBidPrice` относятся только к проверенной форме и моменту чтения, а не гарантируют отсутствие всех альтернативных предложений API.

Единица «фэни CNY за штуку» опирается на сохранённую сверку цен с кабинетом от 18.11.2026; сегодняшний эксперимент не включал новую сверку валюты/единицы с UI. PDF указывает Long Price и cents для supplementary price, но сам по себе не закрывает все единицы полей. Не переносить единицу `supplementPrice[].price` на `minBidPrice` без отдельного источника. SDK должен сохранять исходное значение без float и не угадывать единицы по величине.

Практический способ проверки цены, подтверждённый текущими ответами: отправить `querySkuBidPrice` с явным `hasPrice=true`, сопоставить каждый ответ по dw SKU и выбранному подключению. Успешное отсутствие контрольного SKU в таком ответе в сочетании с ответом без фильтра показывает отсутствие основного предложения `minBidPrice` в проверенной форме для выбранного подключения на момент чтения. Это не свидетельство удаления SKU или доступного количества товара.

Для Global массив 200 различных ID принят (`code=200`, 15 ценовых элементов); 201 ID отклонён (`code=500080002`) при HTTP 200. Контрольный диапазон: `65412561`–`65412760` / `65412761`. Устанавливается работоспособность batch 200 и отказ при 201 на этом запросе, а не наличие товара по каждому ID диапазона. Текущий SDK также ограничивает `dwSkuIds` до 200.

## Наблюдалось: статус не равен предложению

Все три контрольных SKU имели `distStatus=PRODUCT_ON` в обоих подключениях. В частности, SKU `65412648` остаётся в каталоге с `PRODUCT_ON`, но не имеет основного `minBidPrice`/`fulfillmentMode` в ответе цен без фильтра; его `supplementPrice` пуст, а сам SKU исключён при `hasPrice=true`.

`querySkuList` с `distStatus=PRODUCT_ON` вернул эти три ID; с `PRODUCT_OFF` — пустой список, оба раза HTTP 200 / code 200. На заведомо ON-наборе это согласуется с применением фильтра, но **не доказывает**, что снятый SKU будет возвращён как OFF, что он попадёт в incremental-окно либо что фильтр гарантированно поддерживается после deprecation.

Дополнительный Global-запрос `querySpuList(distStatus=PRODUCT_OFF, pageSize=1, startId=0)` без dw-фильтра вернул HTTP 200 / code 200 и **SPU `81971`, запись `id=14`, со статусом `PRODUCT_ON`**, `modifyTime=1775172220000`. Таким образом, SPU-фильтр OFF не обеспечил выдачу только OFF-записей. Причина (игнорирование deprecated-фильтра или иная семантика) не установлена; на него нельзя опираться для обнаружения снятия. Аналогичный единичный запрос `querySkuList` завершился `JsonException` в bootstrap до возврата HTTP-метаданных. Его статус не известен; это не доказанный 504 и не пустой успешный результат. Запрос не повторяли.

Ни один фактически снятый SKU или tombstone в контрольном наборе не наблюдался. Восстанавливать `distStatus` как публичный надёжный механизм отслеживания снятия по этим результатам нельзя.

## Офлайн: различия отсутствия, null и нуля

Девять проверок текущего SDK выполнены в Docker на PHP 8.2.36 без сети и credentials:

- `36900` → точная строка `"36900"`.
- `minBidPrice=0` → `"0"`, `has('minBidPrice')=true`.
- Явный `null` → null при `has()=true`.
- Отсутствующее поле → null при `has()=false`.
- `items=[]` отличается от существующего элемента без поля цены.
- Неизвестный/устаревший статус сохраняется в `extraFields` без бизнес-интерпретации.
- Явное `hasPrice=false` не исчезает из параметров.
- Массив 200 ID принимается DTO, 201 — `InvalidRequestException`.

Это синтетические проверки возможностей представления SDK. Они не подтверждают, что Poizon реально использует zero/null для отсутствующего предложения.

## Воспроизведение

Офлайн из корня репозитория:

```sh
docker run --rm --network none --read-only \
  --mount "type=bind,source=$PWD,target=/package,readonly" \
  poizon-package-test:8.2 \
  php /package/docs/0001-catalog-sync-support/reports/scripts/03-local-price-contract.php
```

Для живого запуска в разрешённый существующий runtime передать через stdin общий bootstrap, затем содержимое живого сценария без повторного открывающего тега `<?php`. Не копировать туда файлы и credentials. Пример с настроенными локально `POIZON_SPIKE_HOST` и `POIZON_SPIKE_CONTAINER`:

```sh
cat docs/0001-catalog-sync-support/reports/scripts/01-live-bootstrap.php \
  <(tail -n +2 docs/0001-catalog-sync-support/reports/scripts/03-live-prices.php) \
  | ssh -o BatchMode=yes -o ConnectTimeout=10 -o StrictHostKeyChecking=yes \
    "$POIZON_SPIKE_HOST" "docker exec -i $POIZON_SPIKE_CONTAINER php"
```

Для отдельного повторного снимка добавить к `docker exec` параметр `-e POIZON_SPIKE03_SNAPSHOT=1`: выполняются только четыре чтения SKU/цены. Для двух точных чтений supplementary-цен — `-e POIZON_SPIKE03_SUPPLEMENT_PROBE=1`. Для одного поиска OFF-записи без товарного фильтра — `-e POIZON_SPIKE03_OFF_PROBE=querySkuList` либо `querySpuList`; это отдельные единичные эксперименты, без повторов при ошибке. Циклы ограничены, по 500 мс между отправками, retry отсутствует. При исключении/401/403/429/5xx сценарий останавливается; исключения выводятся только классом. Пример предназначен для оболочки с process substitution (zsh/bash). Условия нового запуска и текущие данные могут отличаться.

Синтаксис живого сценария проверен PHP 8.2.36; `pint --test` двух сценариев успешен. Сохранённый JSONL разобран как 24 JSON-строки и сопоставлен с матрицей; отдельно сохранён класс единственного исключения без message/trace.
