# Отчёт 01. Временные окна SPU/SKU

## Результат

28.11.2026 на двух точных исторических контрольных записях Global подтверждён включительный отбор `modifyStartTime <= modifyTime <= modifyEndTime` для `querySpuList` и `querySkuList`. Обе одиночные границы применяются. Равное окно `[T,T]` возвращает запись; обратное окно даёт успешный пустой список. Соседние включительные окна дублируют запись на общей границе; объединение после устранения повторов совпало с одним целым окном на контрольных наборах из трёх SPU и трёх SKU.

Исследование задачи 01 принято 28.11.2026, выводы включены в спецификацию и [документацию пакета](../../catalog-sync.md). Эти результаты не закрывают вопросы задач 02–04 о полном изменяющемся каталоге, ценовых событиях, снятии SKU и каналах. Реализация SDK в этом спайке не изменялась.

## Безопасность и воспроизведение

Локальный bank runtime не имел Open Platform настроек и OAuth-таблиц; живые запросы оттуда не делались. Agent Vault discovery показал отсутствие прямого маршрута Poizon. Использован существующий разрешённый production-контур чтений.

[Bootstrap](./scripts/01-live-bootstrap.php) читает access-токен внутри транзакции PostgreSQL `READ ONLY`, расшифровывает его только в памяти и откатывает транзакцию до HTTP-запроса. `AuthorizationManager::resolve`, refresh и изменение credentials не вызываются. Изолированная HTTP factory не передаёт payload прикладным HTTP listeners. Повторы отключены: одна отправка на запрос. Разрешены только четыре операции чтения; покупки и изменение каталога исключены.

Запускать bootstrap и тело соответствующего сценария через stdin в PHP существующего app-контейнера; первую строку `<?php` тела пропустить. На сервере файлы не создаются. Конкретный SSH-контур выбирается оператором; credentials не передаются аргументами.

- [Матрица временных запросов](./scripts/01-time-window-matrix.php): исходная серия из 40 запросов и дополнительная серия из 6 запросов (`unbounded`, `start_only_after`, `end_only_before` для обоих методов). Текущая полная матрица содержит 44 случая; переменная `$poizonTimeCases` позволяет выбрать подмножество для повторения.
- [Сравнение соседних окон](./scripts/01-time-window-partitions.php): 6 запросов на двух наборах из трёх ID.
- [Сохранённые очищенные наблюдения](./01-time-window-observations.jsonl): 52 строки; только бизнес-параметры, товарные ID, `modifyTime`, коды и метаданные.
- [Офлайн-проверка наблюдений](./scripts/01-check-observations.py): запуск в Docker с репозиторием, смонтированным read-only. Проверяет ожидаемый состав, временные границы и равенство множеств.

До сохранённой серии выполнены ещё два точечных чтения SPU/SKU 10903 для выбора контролей; всего в задаче 54 HTTP-чтения. Все 52 сохранённые отправки завершились HTTP 200 / `code=200`, без retry. Это не 52 утверждения об успехе фильтра: выводы основаны на составе записей.

## Контрольные записи

| Метод | Товарный ID | `id` записи | `modifyTime = T` |
| --- | --- | --- | --- |
| SPU | `dwSpuId=10903` | `311943` | `1787786149000` |
| SKU | `dwSkuId=65412648` | `4522488` | `1787181701000` |

Точный фильтр ограничивает возможный результат одним ID. `pageSize=200`; исходный и повторный запрос без времени вернули по одной записи с неизменным T. Поэтому контроль не требует предположений о полноте глобального обхода.

## Результаты матрицы

Одинаковый результат получен для обоих методов:

| Случай | Границы | Контрольная запись |
| --- | --- | --- |
| Нижняя граница до T | `[T−1, T+24ч]` | Есть |
| Нижняя граница ровно T | `[T, T+24ч]` | Есть |
| Нижняя граница после T | `[T+1, T+24ч]` | Нет |
| Верхняя граница до T | `[T−24ч, T−1]` | Нет |
| Верхняя граница ровно T | `[T−24ч, T]` | Есть |
| Верхняя граница после T | `[T−24ч, T+1]` | Есть |
| Только начало T / T+1 | `[T, ∞)` / `[T+1, ∞)` | Есть / нет |
| Только конец T / T−1 | `(-∞, T]` / `(-∞, T−1]` | Есть / нет |
| Равные границы | `[T,T]` | Есть |
| Обратные границы | `[T+1,T]` | Нет; HTTP 200 / code 200, `total=0` |
| Начало в эпохе | `[0,T+1]` | Есть |
| Вместо мс переданы секунды | `[floor(T/1000)−1, floor(T/1000)+1]` | Нет |
| Длительность | 1, 6, 24, 168 часов до `T+1` | Есть во всех случаях |

Временные поля ответа везде остались целыми UTC-миллисекундами. При передаче секунд сервер не умножил их автоматически на 1000: контрольная запись исключена. Отрицательные значения, float, строки неверного формата, отсутствие обеих границ в динамическом полном каталоге и максимальный Long отдельно не исследовались.

## Полнота сравнения целого окна и соседних окон

| Набор | Целое окно `[A,C]` | Левое `[A,B]` | Правое `[B,C]` | Пересечение |
| --- | --- | --- | --- | --- |
| SPU | 10903, 10905, 10906 | 10903, 10905 | 10905, 10906 | 10905 |
| SKU | 849685084, 65412648, 849741572 | 849685084, 65412648 | 65412648, 849741572 | 65412648 |

SPU: A=`1787786149000`, B=`1788477364000`, C=`1788477597000`. SKU: A=`1787181665000`, B=`1787181701000`, C=`1787182104000`. Для каждого ответа `total` совпал с числом записей (3 либо 2); число меньше 200, фильтр содержит ровно три возможных ID. Множество целого окна равно объединению соседних, по одной записи на общей границе повторяется.

Целое SPU-окно длилось 8 суток 4 минуты 8 секунд и тоже было принято на точном наборе. Это дополнительное наблюдение, а не доказательство максимальной длительности или производительности широкого запроса.

## Правила для документации и задачи 05

1. Передавать UTC-миллисекунды как Long без float и без преобразования через `timeZone`.
2. Обе границы опциональны; для воспроизводимого incremental приложение фиксирует начало и конец на весь обход. Наблюдавшаяся семантика обеих границ включительная.
3. Соседнее окно начинать с предыдущей верхней границы, не с `end+1`. Запись на стыке обработать идемпотентно/устранить повтор. Дополнительное перекрытие для задержанных изменений является политикой приложения; необходимая величина задержки этим спайком не установлена.
4. Равное окно не отклонять как заведомо пустое. Нулевое начало upstream принял. Для обратного окна не объявлять обязательную upstream-ошибку: наблюдался успешный пустой результат. В совместимом SDK не выдумывать ограничения этих случаев.
5. Не вводить недоказанный предел 6 часов или 7 суток. Для точечных исторических чтений приняты исследованные длительности; нагрузка и максимальная ширина широкого окна не установлены.
6. Полноту многостраничного каталога подтверждает отдельный спайк 02. Этот эксперимент доказывает отсутствие потерь при разбиении на конечных стабильных контрольных наборах; не гарантирует snapshot isolation, eventual-consistency lag или доставку ценовых/статусных событий.

Блокирующих неизвестных по проверенному контракту границ и контрольного разбиения задачи 01 не осталось. Неизвестные о максимальной длительности и согласованности динамического каталога не подменены гарантиями; SDK не должен заявлять такие гарантии. Готовность всей синхронизации по-прежнему требует результатов остальных спайков.

## Проверка артефактов

Синтаксис трёх исследовательских PHP-файлов проверен в Docker PHP 8.2. Офлайн-проверка JSONL отдельно доказывает все ожидаемые включения/исключения, стабильность контролей и равенство двух объединений. Это проверка сохранённых реальных ответов, а не симуляция upstream.
