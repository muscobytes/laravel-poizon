## Методы и ответы

Базовый путь: `https://open.poizon.com/dop/api/v1/pop/api/v1/market/channel/`. Все перечисленные методы используют POST с плоским JSON: общий OAuth envelope и бизнес-параметры находятся на одном уровне.

| Операция | Источник | Проверенный контракт |
| --- | --- | --- |
| Список SPU | [200002](https://open.poizon.com/doc/list/apiDetail/200002?openKey=22) | `product/querySpuList`, `dwSpuId` — массив, ответ `data.spuList` |
| Список SKU | [200003](https://open.poizon.com/doc/list/apiDetail/200003?openKey=22) | `product/querySkuList`, `dwSkuId` — массив, ответ `data.skuList`; для поиска карточки `hasPrice` не передаётся |
| Карточка SKU | [200004](https://open.poizon.com/doc/list/apiDetail/200004?openKey=22) | `product/querySkuDetail`, проверена комбинация скалярного `dwSpuId` и массива `dwSkuId`, ответ `data.skuList` |
| Цена | [200021](https://open.poizon.com/doc/list/apiDetail/200021?openKey=22) | `product/querySkuBidPrice`, массив `dwSkuIds` до 200 и `hasPrice=true`, ответ `data.items`; `minBidPrice` — цена штуки в фэнях CNY |
| Баланс | [200009](https://open.poizon.com/doc/list/apiDetail/200009?openKey=22), L1/L3 | `order/queryPrepaymentBalance`, единственный принятый DTO — `data.imoneyDTO`: `amount` String, `minUnitVal` Integer, `currency` String |

Для реальных SKU оба направления вернули HTTP 200 / `code=200` по списку SKU, карточке, SPU и цене. `distPlatform` при этих запросах не передавался; угадывать его enum для текущих операций не требуется.

### Подпись массивов и ID

Официальный [клиент документации](https://h5static.poizonapp.com/poizon-open-platform/src__pages__doc__list__apiDetail__$id.b1c5c02b.async.js), модуль `61193`, соединяет элементы примитивного массива запятой и кодирует полученную строку для подписи. Например, `[65412613, 65412626]` даёт фрагмент `dwSkuIds=65412613%2C65412626`. Модуль `19371` и стандартная сериализация Axios сохраняют JSON-массив в POST body. Проверены три offline-вектора с вымышленными credentials и принятие подписанных массивов сервером для обеих авторизаций.

В товарных ответах `dwSkuId/dwSpuId` и `distSkuId/distSpuId` различны. Для одного dw SKU направления возвращают разные dist ID. Адаптер передаёт четыре ID потребителям строками, не использует float и не подменяет товарный ID полем `id` записи. Исходный `orders.sku_id` сохраняется. При последовательной проверке Fast → Global найденный dw ID позволяет адресовать тот же товар через другую привязку.

## Цена и наличие предложения

Контрольный товар: [Nike Air Monarch, SPU 10903](https://poizonresell.com/products?spuId=10903).

| SKU / размер | Fast: ответ цены | Global: ответ цены | Сверка с кабинетом Fast |
| --- | --- | --- | --- |
| `65412613`, EU 42.5 | `36600`, `DEPOSIT` | `36400`, `NORMAL` | Предложения 366 CNY с доставкой около 3 дней и 364 CNY с доставкой около 5–6 дней |
| `65412626`, EU 44 | `39700`, `DEPOSIT` | `39700`, `DEPOSIT` | Цена 397 CNY |
| `65412648`, EU 48 | SKU есть в каталоге, в успешном ответе цен отсутствует | SKU есть в каталоге, в успешном ответе цен отсутствует | Размер недоступен для выбора |

Для отрицательного случая запрос с `hasPrice=true` включал одновременно доступный `65412613` и недоступный `65412648`: в ответе обеих привязок присутствовал только доступный контрольный SKU. Отсутствующий элемент такого успешного ответа означает отсутствие доступного предложения выбранной привязки. Сумма при этом остаётся `null`, а не нулём.

`hasPrice=false` ценового метода возвращал пустой список даже для контрольных SKU с ценой. Поэтому рабочий запрос цены явно передаёт `true`; пустой результат другой формы запроса не используется для вывода о наличии.

Направление выбирает проверенную авторизацию, затем адаптер сопоставляет dw SKU в её ответе. `fulfillmentMode` сохраняется, но не служит фильтром Fast/Global: Global законно вернул `DEPOSIT` для одного из контрольных SKU. Существующий порядок Fast → Global и сравнение общей цены с ДМЦ сохраняются. Общая цена — цена штуки в фэнях × количество / 100.

`minBidPrice` списков/карточки и `supplementPrice[].priceType` не нужны для принятия текущего решения: источником фактической цены является проверенный основной `minBidPrice` метода цен. Его единица подтверждена отдельно от `createOrder.product.price`.

`total` списка означает число записей, а не складской остаток. Прежний алгоритм проверял положительную цену и умножал её на количество; новый контроль остатка `>= quantity` в #47 не вводится. Сетевые ошибки, авторизация, неоднозначные ID и неполная форма ответа не превращаются в отсутствие товара или цену 0. Прямые интеграционные ошибки сохраняют внешний ответ 503/429 без создания заказа и скрытого переключения направления.

## Ограничения исходной проверки, существенные для каталога

- Global сверен по подписанным ответам и наблюдаемым предложениям контрольного товара; отдельный вход в кабинет Global не выполнялся.
- Нефильтрованный список с `pageSize=2` ранее вернул HTTP 504 для обеих привязок; успешные чтения использовали точные товарные фильтры.
- Проверка не доказывает полноту обхода каталога, семантику временных окон, обнаружение снятых SKU или изменение `modifyTime` при смене цены. Эти вопросы должны закрыть спайки проекта.
