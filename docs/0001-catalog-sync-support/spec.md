Статус: спайки 01–04 приняты; спайк 03 принят с консервативными ограничениями по решению владельца 28.11.2026, без ожидания ответа Poizon. ## Цель и границы

Публичный SDK должен передавать подтверждённые параметры full/backfill/incremental-чтений, возвращать описания и цены без потерь. Приложение отвечает за обход страниц, watermark, курсоры, расписание, очереди, устранение повторов, миграцию данных и бизнес-сопоставление Fast/Global.

План и порядок приёмки: [обзор проекта](./README.md). Реализация [05](tasks/completed/05-catalog-sync-support.md) запрещена до завершения спайков [01](tasks/completed/01-spike-time-windows.md), [02](tasks/completed/02-spike-pagination.md), [03](tasks/completed/03-spike-prices-and-delisting.md), [04](tasks/completed/04-spike-channels-and-responses.md). Выпуск выполняется отдельно по [06](./tasks/06-release.md).

## Источники и достоверность

- [Мануал POIZON RESELL: Open API Integration Guide](./sources/poizon-open-api-integration-guide-1029.pdf), локальная копия исходного PDF `POIZON RESELL_ Open API Integration Guide-1029.pdf`. Страницы 13–19 описывают списки; 31–32 — цены. Документ содержит оговорку об AI-generated содержимом, поэтому спорные правила требуют проверки.
- [Выдержка из протокола прежних живых чтений от 18.11.2026](./sources/poizon-read-contract-2026-11-18.md). Это свидетельство конкретных чтений, а не гарантия полноты синхронизации.
- Публичные точки документации: [SPU](https://open.poizon.com/doc/list/apiDetail/200002?openKey=22), [SKU](https://open.poizon.com/doc/list/apiDetail/200003?openKey=22), [цены](https://open.poizon.com/doc/list/apiDetail/200021?openKey=22). Их содержимое не удалось получить публичным web-инструментом при исходной сверке; не считать их независимо проверенными источниками текущего контракта.
- Код и [документация SDK](../../README.md) описывают текущую реализацию, а не доказывают поведение Poizon.

По PDF временные фильтры — Long, UTC-миллисекунды; `querySku` — Boolean с серверным default `true` (default `querySku` отдельно не исследован). Для SPU указан `pageSize` 1–200, для SKU 1–2000; серверные пределы и defaults размера проверены спайком 02. Текущий валидатор SDK допускает до 2000 для обоих списков. `distStatus` помечен устаревшим. PDF описывает числовой `distSpuId` в SPU; baseline DTO принимал только строку, задача 05 добавила приём неотрицательного целого числа; в текущих живых ответах получены UUID-строки.

## Подтверждённые результаты 28.11.2026

- [Спайк 01](./reports/01-time-windows.md): UTC-миллисекунды, обе границы включительны, одиночные границы работают; `[T,T]` не пусто, обратное окно пусто, начало 0 принято. Объединение соседних окон на стабильных тройках SPU/SKU равно целому окну после dedup. Исследованные длительности 1/6/24/168 часов и точный SPU-набор чуть длиннее 8 суток приняты; максимальную ширину не устанавливать по этому наблюдению. Следующее окно начинается с предыдущего конца с устранением повторов. Гарантии задержки/динамического снимка отсутствуют.
- [Спайк 02](./reports/02-pagination.md): SPU выше 200 и SKU выше 2000 сервер отклоняет business code `10002001` при HTTP 200. Defaults на достаточном наборе — 100 SPU / 500 SKU. `lastId`/`hasMore` отсутствуют; курсор `startId` исключительный по `id` записи, не dw ID. Обходы SPU 8 и SKU 25 записей с разными страницами дали одинаковые множества. Конец — успешная пустая страница; `total` на непустых страницах — размер исходного набора, на пустой 0. Приложение проверяет продвижение `max(id)` и сохраняет фиксированные фильтры/окно и авторизацию.
- [Спайк 03](./reports/03-prices-and-delisting.md): в контрольных списках `minBidPrice` отсутствует; отдельный метод цен работает. Без `hasPrice` возвращены 3 элемента, с `true` — 2 с ценой, с `false` — 1 без основной цены, с пустым `supplementPrice`. Batch 200 принят, 201 отклонён code `500080002` при HTTP 200. `PRODUCT_ON` не означает наличие основной цены. SPU-запрос с `distStatus=PRODUCT_OFF` вернул `PRODUCT_ON`: надёжность deprecated-фильтра не подтверждена. SKU OFF-probe завершился ошибкой декодирования без сохранённого HTTP-статуса. Реальных переходов цены/снятия не наблюдалось; гарантия изменения `modifyTime` и механизм обнаружения снятых SKU не подтверждены; эти вопросы не входят в гарантии текущего SDK и вынесены в отдельное уточнение. Подготовленный запрос Poizon (китайский + русский перевод) не отправлялся.
- [Спайк 04](./reports/04-channels-and-responses.md): 8/8 чтений двух авторизаций без `distPlatform` успешны. Реальный `productDesc` доступен через `extraFields`; dist ID — разные UUID между каналами при одинаковых dw ID. Родительские SPU ID во вложенных SKU и dist ID в ценовых элементах могут отсутствовать. 15 синтетических проверок на PHP 8.2/8.4 подтвердили точные большие ID, присутствие/null и дополнительные структуры. На baseline спайка числовой SPU `distSpuId` отклонялся схемой DTO, а не округлялся; задача 05 добавила его приём без изменения исходных доказательств. `fulfillmentMode` не означает канал.

Живые спайки использовали production signer/transport предшественника SDK (образ приложения `53e06e155098dc69b26e25c09c398e779d4fd8d4`), доступные в runtime; standalone SDK там не установлен. Проверенная локальная ревизия SDK — `1898169f1fd0e94e909f4ab8950481da6fde0173`. Это доказательства протокола на контрольных наборах и отдельные проверки DTO, не полная живая приёмка будущего `PoizonClient`.

## Исследовательский контракт

Спайки запускаются вручную в изолированном Docker-контейнере, вне PHPUnit и CI. Использовать существующие разрешённые авторизации и SDK для транспорта, подписи и OAuth. При необходимости экспериментальный адаптер передаёт отсутствующие параметры, не расширяя стабильный API и не дублируя реализацию подписи.

Не выполнять покупки, изменения каталога и принудительный refresh; не допускать изменения credentials исследовательским запуском. При невозможности чтения без таких изменений остановить эксперимент и записать блокер. Ограничивать объём чтений контрольными наборами; при 429 соблюдать `Retry-After` и не запускать безграничные повторы.

Отчёт содержит цель, дату и часовой пояс, окружение/ревизию SDK, обезличенный псевдоним подключения, очищенные бизнес-параметры, HTTP/upstream-коды, число отправок, состав записей, курсоры, наблюдение и вывод. Credentials, OAuth envelope, подписи, персональные данные и исходные секретные ответы не сохранять. Идентификаторы товара допускаются как воспроизводимые контрольные примеры.

Для каждого правила различать: документировано, наблюдалось в эксперименте, осталось неизвестным. Указывать предел применимости. HTTP 200 без проверки состава ответа не доказывает работу фильтра. 429, 504, транспортные и OAuth-ошибки не означают пустой каталог. Ненаблюдавшийся переход состояния нельзя объявлять проверенным.

Неразрешённые вопросы закрываются дополнительным спайком либо официальным ответом Poizon с датой и источником. Сообщение в поддержку готовится на китайском с русским переводом; отправка — только по отдельному поручению. Первоначально такие вопросы блокировали приёмку. По решению владельца от 28.11.2026 спайк 03 принят с описанными ниже ограничениями; неизвестные факты не считаются подтверждёнными.

Каждый спайк сохраняет содержательный отчёт, добавляет ссылку в README проекта, обновляет эту спецификацию и релевантные правила в публичной документации пакета. Реализованные в задаче 05 параметры документируются отдельно от исторического состояния спайков. Пустые отчёты и вымышленные результаты запрещены.

## Временно принятое решение по спайку 03 — 28.11.2026

По поручению владельца продолжить реализацию до ответа Poizon приняты следующие правила:

1. Приложение выполняет отдельный периодический обход известных SKU через `querySkuBidPrice` пакетами до 200 ID и при необходимости проверку цены перед бизнес-действием. Не полагаться на `modifyTime` для полноты цен. Расписание и квоты определяет приложение, SDK их не реализует.
2. `hasPrice=true` подходит для чтения основных цен; ответ без фильтра позволяет различать элементы с основным полем цены и без него. Отсутствие элемента, отсутствие поля, null, ноль и ошибка не объединяются. Отсутствие основного предложения не означает снятие SKU.
3. Не добавлять `distStatus` как надёжный фильтр/enum SDK. Поле ответа сохранять через `extraFields`. Не удалять и не помечать SKU снятым по отсутствию в incremental, отсутствию цены либо deprecated-статусу; состояние снятия для приложения остаётся неизвестным без отдельного подтверждения. SDK не вводит новое доменное состояние или автоматическую бизнес-реакцию.
4. Выполненные эксперименты и неизвестные гарантии остаются в отчёте. Принятие ограничений — продуктовое решение, не новое подтверждение Poizon. [Отдельная задача уточнения](../0000-backlog/tasks/02-confirm-price-and-delisting-contract.md) не является зависимостью 05/06; вернуться к ней после официального ответа или воспроизводимого перехода.
5. Спайк 03 закрывается с ограничениями, 05 разблокируется. Совместимый SDK можно выпустить с честным описанием этих границ; обещание полного отслеживания снятых SKU в выпуск не входит.

## Публичные запросы

| DTO | Дополнение | Входной контракт |
| --- | --- | --- |
| `SpuListQuery` | `querySku` | Boolean либо отсутствие |
| `SpuListQuery` | `modifyStartTime`, `modifyEndTime` | Целое число или строка десятичных цифр; UTC-миллисекунды |
| `SkuListQuery` | `modifyStartTime`, `modifyEndTime` | Аналогично SPU |

- Добавить аргументы в конец конструкторов; сохранить прежние позиционные и именованные вызовы.
- Для новых параметров default `null` означает отсутствие. Конструктор и `fromArray()` одинаково трактуют явный `null` как отсутствие и одинаково проверяют исходные типы до неявного scalar-приведения PHP. Строки `"false"`, числа 0/1 не принимать за Boolean.
- `querySku=false` передаётся в body и подписи. При отсутствии параметра не подставлять `true` на клиенте.
- Временные значения проверять существующим механизмом Long, без float, преобразования часового пояса и эвристического умножения секунд. Спайк 01 подтвердил нулевое начало, одиночные и равные границы; обратное окно upstream обрабатывает пустым результатом. Не вводить новых запретов этих случаев либо недоказанного максимума длительности.
- Неизвестные/зарезервированные ключи отклонять. Проверки новых полей не должны менять контракты остальных Query-классов.
- Использовать подтверждённые пределы SPU 200 / SKU 2000 и defaults 100 / 500 в документации и примерах. Сервер отклоняет превышение, не обрезает его молча в проверенных случаях. В совместимом выпуске не ужесточать прежний валидатор скрыто. Если необходимо несовместимое изменение, выделить его отдельно с minor-версией до 1.0.

## Ответы, статусы, цены и каналы

- `Spu.distSpuId`: реализован приём неотрицательного целого числа с возвратом строки. Существующие строки сохранять; float отклонять. Не сужать строковые dist ID до одних цифр.
- Сохранить `JSON_BIGINT_AS_STRING`, строковые идентификаторы и точные строки цен. Числовой JSON `distSpuId` до задачи 05 вызывал ошибку типа; задача 05 нормализует int в строку локально в Spu::fromArray. Новой потери точности декодера не обнаружено.
- Пагинация остаётся в существующих `lastId`, `hasMore`, `total`; смысл и наличие каждого поля подтверждаются спайком. Не выдавать `total` за складской остаток.
- Отсутствие поля и явный `null` различать через `has()`; `fields()` и `extraFields` сохраняют доступ к дополнительным данным после очистки секретов.
- `id`, `modifyTime`, `productDesc`, статусы и дополнительные описания использовать через `extraFields`, если это обеспечивает контракт без потерь. Новые типизированные поля добавлять только при доказанном ограничении существующего API.
- Источник основной цены — существующий `querySkuBidPrice`, до 200 ID за запрос, с явным выбором `hasPrice` по результатам спайка 03. SDK не выполняет пересчёт, округление и бизнес-интерпретацию отсутствия предложения.
- Если цена не меняет `modifyTime`, документировать отдельный периодический обход цен в приложении. Аналогично определить рабочую процедуру обнаружения снятых SKU. Отсутствие предложения не равно удалению товара; устаревший `distStatus` не восстанавливать без подтверждения.
- Не считать incremental полным источником ценовых/статусных событий. Приложение отдельно обновляет цены; снятие остаётся неизвестным без надёжного подтверждения. Принятое ограничение спайка 03 разблокирует 05 и выпуск поддерживаемых возможностей, но не обещает полноту миграции бизнес-статусов каталога.
- Выбор авторизации переиспользует `AuthorizationReference`; сопоставление подключения с Fast/Global выполняет приложение. `fulfillmentMode` не считать фильтром каналов. Общий параметр протокола добавлять только при доказанной необходимости по спайку 04.
- Транспорт, подпись, retry, диагностику и хранение OAuth переиспользовать. Ошибки чтений не превращать в пустые успешные результаты или нулевую цену.

## Проверка, документация и выпуск
