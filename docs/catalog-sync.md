# Чтение каталога: подтверждённый протокол и ограничения SDK

Проверено 28.11.2026 на ограниченных контрольных наборах Poizon. Живые чтения выполнялись через существующие Fast/Global-авторизации и production-предшественник транспорта/подписи SDK; текущие DTO проверялись отдельно в Docker. Это не проверка установки новой версии SDK и не гарантия стабильного снимка всего каталога.

План и отчёты: [проект 0001](./0001-catalog-sync-support/README.md). Начиная с версии `0.1.1` реализованы `SpuListQuery::querySku`, `modifyStartTime` и `modifyEndTime` обоих списков. Для установки этих возможностей используйте `composer require muscobytes/laravel-poizon:^0.1.1`; версия `0.1.0` их не содержит.

## Параметры SDK и примеры одного шага

| DTO | Новые параметры | Правила |
| --- | --- | --- |
| `SpuListQuery` | `querySku` | Только bool или null; false передаётся в запросе и подписи, null/отсутствие не подставляют серверное значение |
| `SpuListQuery`, `SkuListQuery` | `modifyStartTime`, `modifyEndTime` | Неотрицательный Long: int или строка цифр до PHP_INT_MAX, UTC-миллисекунды, нормализуется в int |

Конструктор и `fromArray()` одинаково проверяют новые поля до неявного PHP-приведения. Null новых параметров означает отсутствие; строка `"false"`, 0/1 вместо bool, float вместо времени, отрицательное значение и переполнение отклоняются `InvalidRequestException`. Неизвестные поля запрещены. Старые аргументы и локальные пределы `pageSize` сохранены. SDK не вводит недоказанный максимум окна, не отклоняет равное или обратное окно только из-за отношения границ.

```php
use Muscobytes\Poizon\Data\Requests\{SpuListQuery, SkuListQuery};

// Одна страница full-чтения; серверный предел SPU — 200.
$full = $client->querySpuList($authorization, new SpuListQuery(pageSize: 200, querySku: true));

// Один шаг backfill: курсор сохранён приложением после обработки предыдущей страницы.
$backfill = $client->querySpuList($authorization, SpuListQuery::fromArray([
    'startId' => $savedCursor,
    'pageSize' => 200,
    'querySku' => false,
]));

// Одна страница incremental: обе границы зафиксированы на весь проход приложением.
$incremental = $client->querySkuList($authorization, new SkuListQuery(
    startId: $windowCursor,
    pageSize: 2000,
    modifyStartTime: $windowStartMs,
    modifyEndTime: $windowEndMs,
));
```

Приложение сохраняет курсор после успешной записи страницы, watermark — после успешного завершения всего окна. Обход, блокировки параллельных запусков, перекрытие окон и устранение повторов остаются его обязанностью; SDK возвращает ровно одну страницу. Переменные примеров — сохранённое состояние приложения, а не новые настройки SDK.

## Временные окна

Живой спайк на Global подтвердил для SPU и SKU условие `modifyStartTime <= modifyTime <= modifyEndTime`: UTC timestamp в миллисекундах, обе границы включены. Проверены попадание записи на `T`, исключение на `T±1` с другой стороны границы и работа каждой одиночной границы. `[T,T]` возвращает запись; обратное окно вернуло успешный пустой список; начало `0` принято. Сервер не исправляет переданные вместо миллисекунд секунды.

Приложению следует фиксировать обе границы на весь обход и начинать соседнее окно с предыдущего конца, устраняя повторы на стыке. На стабильных наборах из трёх SPU и трёх SKU объединение соседних окон совпало с целым окном; запись общей границы присутствовала в обоих соседних ответах.

Окна 1, 6, 24, 168 часов приняты; дополнительный точный SPU-набор принят в окне чуть длиннее восьми суток. Максимальная ширина и допустимая нагрузка широкого запроса не установлены. Не вводите предел 6 часов или 7 суток как правило Poizon. Необходимое перекрытие для задержанных изменений, snapshot isolation и влияние цен/статусов на `modifyTime` этими наблюдениями не доказаны.

Методика, исходные границы и очищенные ответы — в [отчёте 01](./0001-catalog-sync-support/reports/01-time-windows.md).

## Размеры страниц и курсор

| Метод | Подтверждённый `pageSize` | Без `pageSize` | Сверх предела |
| --- | --- | --- | --- |
| `querySpuList` | 1–200 по PDF; границы и выбранные размеры проверены живыми чтениями | 100 записей на достаточном наборе | 201, 500, 2000 отклонены: HTTP 200 / code `10002001` |
| `querySkuList` | 1–2000 по PDF; 1999/2000 приняты | 500 записей на достаточном наборе | 2001 отклонён: HTTP 200 / code `10002001` |

Текущий SDK локально допускает SPU `pageSize` до 2000. Это не означает принятия сервером; для SPU используйте до 200. Совместимое расширение SDK также не ужесточает прежний локальный предел; серверный предел указан явно.

В проверенных ответах есть `total` и список; `lastId` и `hasMore` **отсутствуют**. Их nullable-свойства DTO нельзя трактовать как готовый сигнал продолжения. `total` на непустых страницах сохранял размер исходного фильтрованного набора, на пустой странице был 0.

Курсор — `id` записи (доступен через `extraFields['id']`), а не `dwSpuId`/`dwSkuId`. Следующая страница с `startId = max(id)` вернула строго большие ID. Для полного SPU-набора из 8 записей и SKU-набора из 25 записей обходы с разными размерами страниц дали одинаковые множества без повторов. Надёжно проверенный критерий завершения — дополнительная успешная пустая страница: последняя непустая может быть полной. Ошибка HTTP или business code не считается концом; отсутствие продвижения курсора — ошибка обхода.

Все страницы прохода должны использовать одну авторизацию и неизменные фильтры/окно. Курсор относится к этому проходу; не переносите его между каналами. Приложение сохраняет прогресс после успешной обработки страницы. Эксперимент на стабильных наборах не доказывает согласованность изменяющегося всего каталога.

Подробные обходы и проверка серверных defaults — в [отчёте 02](./0001-catalog-sync-support/reports/02-pagination.md).

## Цены и снятие SKU: подтверждённая часть и блокер

В проверенных списках SKU и вложенных SKU SPU поле `minBidPrice` отсутствовало. Рабочий способ отдельной проверки основной цены — существующий `querySkuBidPrice`; текущий SDK принимает до 200 `dwSkuIds`. Живой batch из 200 ID принят, 201 ID отклонён: HTTP 200 / code `500080002`.

Для трёх контрольных SKU через обе авторизации получена такая матрица:

| `hasPrice` | Результат |
| --- | --- |
| Не передан | 3 элемента: 2 с `minBidPrice`, 1 без него |
| `true` | Только 2 элемента с основной ценой |
| `false` | 1 элемент без `minBidPrice`/`fulfillmentMode`, с `dwSkuId` и пустым `supplementPrice` |

Фильтр относится к форме ценового ответа, а не к существованию товара в каталоге. SKU `65412648` в обеих авторизациях имеет `PRODUCT_ON`, но отсутствует при `hasPrice=true`; без фильтра он возвращается без основной цены. Это не доказывает удаление товара, доступное количество или отсутствие всех возможных альтернативных предложений.

Пример текущего API:

```php
$prices = $client->querySkuBidPrice(
    $authorization,
    new \Muscobytes\Poizon\Data\Requests\SkuPriceQuery(
        dwSkuIds: ['65412613', '65412626', '65412648'],
        hasPrice: true,
    ),
);
foreach ($prices->data->items as $item) {
    $skuId = $item->dwSkuId;
    $rawPrice = $item->minBidPrice; // Точная строка, без float и округления.
}
```

Сопоставляйте ответы по dw SKU и выбранному подключению. Отсутствие элемента, отсутствие поля, явный `null` и строка `"0"` — разные состояния; наличие поля проверяется через `has()`. Ноль и явный null в живой матрице не встретились: их представление проверено синтетически и не задаёт семантику Poizon. Ценовые элементы не содержали `currency`; единица «фэни CNY за штуку» подтверждена прежней сверкой с кабинетом 18.11.2026, а не новой сверкой UI в этом запуске.

**Надёжный механизм снятия пока не подтверждён.** В отдельном Global-запросе `querySpuList(distStatus=PRODUCT_OFF, pageSize=1, startId=0)` вернулся SPU `81971` со статусом `PRODUCT_ON`. Фильтр противоречит ожидаемому отбору; его применение/игнорирование после deprecation нельзя считать надёжным контрактом. Дополнительный SKU-запрос завершился ошибкой декодирования, его HTTP-статус не сохранён; такой отказ не считается пустым списком снятых товаров.

Повторные снимки не поймали смену цены или доступности. Гарантия изменения `modifyTime` при каждом таком переходе и попадания в incremental не установлена. Пока она неизвестна, нельзя считать временной проход единственным источником обновления цен; отдельный обход цен выполняется приложением. Он сам по себе не решает обнаружение снятых SKU. До подтверждения протокола приложение не должно удалять или помечать SKU снятым по отсутствию в incremental, отсутствию основной цены либо deprecated-статусу; состояние снятия остаётся неизвестным. SDK не добавляет автоматическую бизнес-интерпретацию этих случаев.

[Отчёт 03 и подготовленный запрос Poizon с русским переводом](./0001-catalog-sync-support/reports/03-prices-and-delisting.md) фиксируют оставшиеся вопросы. По решению владельца 28.11.2026 задача 03 принята с ограничениями, и контракт 05 реализован в рабочем коде; ответ Poizon не является условием выпуска подтверждённых возможностей SDK. Запрос в поддержку не отправлялся. Открытые гарантии вынесены в [задачу уточнения](./0000-backlog/tasks/02-confirm-price-and-delisting-contract.md).

## Fast/Global и описания

Восемь чтений SPU, SKU, карточки и цен через обе авторизации успешны без `distPlatform`. Соответствие подключения каналу задаёт приложение, используя `AuthorizationReference::forConnection()`; `fulfillmentMode` описывает способ исполнения, а не канал. Global вернул в контрольной выборке и `NORMAL`, и `DIRECT_SEND`; прежние наблюдения также содержат `DEPOSIT` для Global.

Одни dw ID в разных подключениях имеют разные UUID-строки dist ID. Нельзя объединять товары между каналами только по dist ID. Вложенный SKU может не содержать родительские SPU ID; ценовой элемент может не содержать `distSkuId`.

Реальный SPU `10903` в обоих подключениях содержит непустой `productDesc`. Поле доступно через существующий API:

```php
$response = $client->querySpuList(
    $authorization,
    new \Muscobytes\Poizon\Data\Requests\SpuListQuery(dwSpuId: ['10903'], pageSize: 1),
);
$spu = $response->data->spuList[0] ?? null;
$descriptionWasReturned = $spu?->has('productDesc') ?? false;
$description = $spu?->extraFields['productDesc'] ?? null;
```

Отсутствующее поле и явный `null` имеют разное присутствие через `has()`. `extraFields` сохраняет дополнительные описания, `modifyTime`, неизвестные вложенные структуры, `null` и `false`; заранее расширять DTO для этих полей не требуется.

## Идентификаторы и точность

Проверки настоящего декодера SDK на PHP 8.2 и 8.4 сохранили JSON-числа `9007199254740993` и `9223372036854775808` точными строками. Сохраняйте `JSON_BIGINT_AS_STRING`, не используйте float для идентификаторов и цен.

В живых SPU `distSpuId` был UUID-строкой. Мануал также описывает числовой вариант: `Spu::fromArray(['distSpuId' => 12345])` теперь возвращает `"12345"`. Отрицательные int, float и bool отклоняются; существующие строки (включая opaque ID и пустую строку) сохраняют прежнее поведение. До задачи 05 числовой вариант вызывал отказ типа, а не округление; это историческое наблюдение отчёта 04, исправленное новым кодом.

Подробные текущие наблюдения, формы ответов, синтетические проверки и ограничения — в [отчёте 04](./0001-catalog-sync-support/reports/04-channels-and-responses.md).
